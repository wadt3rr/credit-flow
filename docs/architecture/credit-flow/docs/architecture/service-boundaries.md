# Credit Flow Microservices — границы сервисов

**Статус:** Draft v1 · **Версия:** 1.0

## 1. Архитектурные принципы
1. Один сервис — одна бизнес-ответственность.
2. Каждый сервис — единственный владелец своих таблиц и правил изменения данных.
3. Прямое чтение/изменение чужих таблиц запрещено.
4. REST — внешний API; gRPC — внутренние запросы, когда нужен немедленный ответ; Kafka — асинхронные события.
5. Все сетевые вызовы имеют timeout; повторы ограничены и безопасны.
6. Распределённый процесс не маскируется под одну ACID-транзакцию.
7. Контракты версионируются; изменения фиксируются документами/ADR.

## 2. Семь бизнес-сервисов

### Identity Service
**Владеет:** пользователи, password hashes, глобальные роли, refresh-сессии.  
**Не владеет:** компаниями, заявками, продуктами и решениями.  
**API:** register/login/refresh/logout/profile.

### Company Service
**Владеет:** компании, реквизиты, участники и роли внутри компании.  
**API:** создание/просмотр/изменение компании, список компаний пользователя, управление членством.  
**События:** `CompanyCreated`, `CompanyUpdated`, `CompanyMemberChanged`.

### Product Service
**Владеет:** продукты, версии условий, публикация и доступность.  
**API:** публичный каталог и административное управление.  
**События:** `ProductPublished`, `ProductRetired`.

### Application Service
**Владеет:** заявки, публичный статус, история переходов, снимок условий, idempotency keys, Outbox.  
**Ключевое правило:** только этот сервис меняет публичный статус заявки.  
**API:** draft/edit/submit/cancel/list/details/history; защищённая административная команда resume для приостановленного процесса.  
**Владеет также:** внутренним состоянием processing hold и оркестрацией восстановления Saga.  
**События:** `ApplicationSubmitted`, `ApplicationReadyForDecision`, `ApplicationStatusChanged`, `ApplicationCancelled`, `ApplicationProcessingHeld`, `ApplicationProcessingResumed`.

### Verification Service
**Владеет:** проверки, метаданные документов, результаты, причины и технические состояния.  
**Не владеет:** публичным статусом заявки и финальным решением.  
**События:** `VerificationStarted`, `VerificationCompleted`, `VerificationFailedTechnically`.

### Decision Service
**Владеет:** версии демонстрационных правил, результаты и факторы решения, идентификаторы запусков.  
**Не владеет:** публичным статусом заявки.  
**События:** `DecisionCompleted`.

### Notification Service
**Владеет:** уведомления, шаблоны, попытки доставки, статус прочтения.  
**API:** список, детали, отметка прочтения.

API Gateway, Kafka, PostgreSQL, observability stack и web client не считаются бизнес-сервисами.

## 3. Хранилища
У каждого сервиса отдельная PostgreSQL database и роль БД. В локальном окружении базы могут находиться в одном PostgreSQL container. Между базами нет foreign keys и JOIN. Межсервисные ссылки — UUID; актуальность проверяется API/событиями с учётом eventual consistency.

## 4. Взаимодействия
**Синхронно:** клиент → Gateway → сервис; Application → Company для проверки членства; Application → Product для получения версии условий. Внутренний RPC — gRPC, с timeout и trace context.

**Асинхронно:** Application публикует submit; Verification публикует результат; Application инициирует Decision; Decision публикует результат; Application фиксирует итог; Notification реагирует на статус.

Gateway отвечает за маршрутизацию, лимиты, корреляцию и общие заголовки, но не содержит бизнес-правил и не является единственным местом авторизации.

## 5. Распределённые процессы
- Outbox связывает локальную транзакцию с будущей публикацией.
- Inbox/deduplication связывает входное событие с локальным изменением.
- Consumers идемпотентны; Kafka не гарантирует однократный бизнес-эффект во всей системе.
- Публичный статус заявки меняет только Application Service.
- Техническая ошибка не трактуется как бизнес-отказ.
- Приостановка обработки не является публичным статусом заявки.
- Resume-команды проверяются на авторизацию, идемпотентность, версию процесса и терминальность заявки.
- Saga/оркестрация хранит явные состояния и правила восстановления; компенсации — бизнес-операции, а не распределённый rollback.

## 6. Репозиторий и структура
Используем монорепозиторий, но каждый сервис имеет отдельный бинарный файл, конфигурацию, миграции, зависимости и Docker image.

Ориентир:
- `cmd/<service>/`
- `internal/<service>/`
- `api/openapi/`
- `api/proto/`
- `migrations/<service>/`
- `deploy/compose/`, позднее `deploy/helm/`
- `tests/integration/`, `tests/contract/`, `tests/e2e/`
- `docs/architecture/`, `docs/adr/`, `docs/runbooks/`

Общие пакеты допустимы для логирования, конфигурации, telemetry и транспортных примитивов; не создаём общую доменную модель всех сервисов.

## 7. Последовательность реализации
1. Identity + Company.
2. Product.
3. Application: draft, state transitions, snapshot, Outbox.
4. Kafka plumbing: publisher, consumer, Inbox, retries, DLQ.
5. Verification + Decision.
6. Notification.
7. Gateway, web UI, observability и эксплуатационные тесты.

## 8. Критерии приёмки
У каждой сущности один владелец; нет доступа к чужим таблицам; контракты документированы; сетевые вызовы ограничены таймаутами; Application — владелец публичного статуса; Outbox/Inbox покрыты тестами; сервисы собираются независимо.
