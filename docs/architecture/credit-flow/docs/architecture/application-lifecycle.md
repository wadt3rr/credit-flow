# Credit Flow Microservices — жизненный цикл заявки

**Статус:** Draft v1 · **Версия:** 1.1  
**Владелец публичного состояния и оркестрации процесса:** Application Service.

## 1. Публичные статусы
- `DRAFT` — черновик; разрешено редактирование допустимых полей.
- `SUBMITTED` — заявка подана и сохранена для обработки.
- `VERIFYING` — выполняются обязательные проверки.
- `UNDER_REVIEW` — проверки пройдены, выполняется принятие решения.
- `APPROVED` — демонстрационное положительное решение.
- `REJECTED` — отрицательное бизнес-решение либо окончательный бизнес-неуспех проверки согласно зафиксированной политике.
- `CANCELLED` — отменена в разрешённой точке процесса.

`APPROVED`, `REJECTED`, `CANCELLED` терминальны в MVP. Техническая приостановка процесса не является публичным статусом и не добавляет значение `BLOCKED` в этот enum.

## 2. Допустимые переходы

| Из | В | Условие |
|---|---|---|
| `DRAFT` | `SUBMITTED` | Submit прошёл валидацию |
| `DRAFT` | `CANCELLED` | Пользователь отменил черновик |
| `SUBMITTED` | `VERIFYING` | Application обработал запуск проверок |
| `SUBMITTED` | `CANCELLED` | Отмена разрешена до критического этапа |
| `VERIFYING` | `UNDER_REVIEW` | Все обязательные проверки успешны |
| `VERIFYING` | `REJECTED` | Окончательный бизнес-неуспех по утверждённой политике |
| `VERIFYING` | `CANCELLED` | Процесс допускает согласованную отмену |
| `UNDER_REVIEW` | `APPROVED` | Валидное положительное решение |
| `UNDER_REVIEW` | `REJECTED` | Валидное отрицательное решение |
| `UNDER_REVIEW` | `CANCELLED` | Только если политика явно разрешает отмену |

Другие переходы запрещены. Реализовать явной доменной политикой.

## 3. Внутренние состояния этапов и приостановка
Verification: `PENDING`, `IN_PROGRESS`, `PASSED`, `FAILED_BUSINESS`, `RETRYABLE_ERROR`, `FAILED_TECHNICAL`, `CANCELLED`.

Decision: `PENDING`, `IN_PROGRESS`, `COMPLETED`, `RETRYABLE_ERROR`, `FAILED_TECHNICAL`.

Техническая ошибка не означает бизнес-отказ. Если автоматические повторы исчерпаны, заявка сохраняет текущий публичный статус, а обработка может быть приостановлена до устранения причины. Внутреннее состояние приостановки (`processing hold`) хранится отдельно от публичного статуса.

Минимальная модель приостановки:
- `hold_id` — идентификатор конкретной приостановки;
- `hold_type` — `TECHNICAL`, `DATA_ISSUE` или `MANUAL_REVIEW`;
- `reason_code` — безопасный машинно-читаемый код причины;
- `stage` — этап, на котором остановлена обработка (`VERIFICATION` или `DECISION`);
- `created_at`, `created_by` — время и инициатор приостановки;
- `resolved_at`, `resolved_by` — время и инициатор снятия приостановки;
- `retry_count` — число попыток для текущего этапа;
- `process_version` — версия процесса, к которой относится приостановка.

Для MVP текущее состояние hold может храниться в агрегате заявки. История приостановок и возобновлений должна сохраняться в аудите/истории операций; если требуется несколько независимых или параллельных hold, модель расширяется отдельной таблицей.

## 4. Submit
Application Service:
1. Аутентифицирует пользователя и проверяет право действовать от имени компании.
2. Проверяет владение заявкой и статус `DRAFT`.
3. Валидирует поля.
4. Получает актуальные опубликованные условия и сохраняет snapshot.
5. Проверяет сумму/срок по продукту.
6. В одной транзакции обновляет статус, пишет историю, сохраняет idempotency result и Outbox event.
7. Возвращает `202 Accepted` после фиксации процесса.

Если продукт временно недоступен и snapshot ещё не сохранён, нельзя сообщать об успешной подаче. Повтор уже успешно выполненной операции обрабатывается через idempotency key.

## 5. Идемпотентность
Для create/submit и команд управления процессом используется `Idempotency-Key` либо эквивалентный уникальный `command_id`, ограниченный субъектом, заявкой и типом операции:
- хранить hash нормализованного запроса и результат;
- одинаковый ключ + одинаковое тело возвращает согласованный результат;
- одинаковый ключ + другое тело возвращает `409 Conflict`;
- уникальный индекс защищает от конкурентного выполнения;
- срок хранения ключей задаётся политикой;
- идемпотентность не заменяет авторизацию и проверку состояния.

Повтор команды `resume` с тем же идентификатором не должен запускать вторую обработку. Для одного этапа и одной версии процесса допускается только один активный запуск.

## 6. Конкурентные переходы
Использовать optimistic concurrency (`version`) или условный `UPDATE ... WHERE status = expected`. Проверка и изменение атомарны. Из двух несовместимых конкурентных переходов фиксируется только один; второй возвращает конфликт либо трактуется как идемпотентный повтор той же операции.

При возобновлении также проверять `process_version`, текущий статус, наличие активного hold и отсутствие уже запущенного выполнения этапа.

## 7. Восстановление и повторный запуск
Различать три сценария:

1. **Автоматический технический retry.** Для временных инфраструктурных ошибок; ограниченное число попыток, exponential backoff и jitter. Retry не меняет публичный статус сам по себе.
2. **Ручное возобновление.** Уполномоченный администратор может возобновить приостановленный этап после проверки причины и, если нужно, устранения неисправности. Предварительный административный endpoint: `POST /admin/v1/applications/{applicationId}/resume`. Он доступен только через защищённый Gateway/административный контур и требует авторизации, `command_id`/`Idempotency-Key` и аудита. Внутренняя доменная команда — `ResumeApplication`.
3. **Повтор после исправления данных.** Допустим только если бизнес-политика разрешает продолжить текущую заявку после корректировки данных. Исправление, основание и новая попытка фиксируются; предыдущие результаты и история не удаляются.

При успешном resume Application Service атомарно проверяет право инициатора, состояние заявки, hold, этап и версию процесса; снимает hold, фиксирует аудит и публикует командное/процессное сообщение через Outbox. Внешняя система не должна напрямую менять статус или таблицы другого сервиса.

Правила восстановления:
- технический сбой не переводит заявку в `REJECTED`;
- повтор не создаёт новую заявку, не сбрасывает историю и не обнуляет общий счётчик попыток;
- у каждой попытки есть `attempt_id`; повтор одного события не создаёт повторный бизнес-эффект;
- для одного этапа и версии процесса не запускаются два активных выполнения;
- результаты устаревшего процесса игнорируются;
- обычный retry/resume запрещён для `APPROVED`, `REJECTED` и `CANCELLED`;
- повторное рассмотрение после `REJECTED` — отдельный бизнес-процесс, не входит в MVP;
- `MANUAL_REVIEW` нельзя снять автоматическим retry; необходима авторизованная операция.

## 8. Обработка событий
- `ApplicationSubmitted`: запускает процесс проверок; повтор не создаёт второй процесс.
- `VerificationCompleted`: проверяет application ID и process version; при успешных обязательных проверках переводит заявку в `UNDER_REVIEW` и публикует `ApplicationReadyForDecision`; бизнес-неуспех обрабатывает по политике.
- `DecisionCompleted`: проверяет process version, rule-set version и уникальность результата; валидный результат переводит заявку в `APPROVED`/`REJECTED`.
- `ApplicationProcessingHeld` и `ApplicationProcessingResumed` фиксируют изменения внутреннего состояния обработки, но не являются публичными переходами статуса.
- Запоздавшие события отменённого/устаревшего процесса не меняют терминальную заявку и не снимают hold автоматически.

## 9. Saga и отмена
Процесс длительный и распределённый. Для MVP Application Service оркестрирует его, храня состояние и инициируя шаги событиями. Отмена — бизнес-команда, а не попытка удалить опубликованные события. Поздние результаты не должны возобновлять отменённый процесс. Восстановление Saga должно быть явным и наблюдаемым; технический retry не равен компенсации.

## 10. История и аудит
Для каждого публичного перехода хранить application ID, предыдущий/новый статус, timestamp, actor/source, correlation ID, безопасный reason code и версию записи. Для hold/resume дополнительно хранить hold ID, тип и причину, этап, attempt ID, инициатора и команду. История неизменяема обычными пользовательскими операциями. Секреты и избыточные персональные данные в аудит не записывать.

## 11. Критерии приёмки
- Тесты всех разрешённых и запрещённых переходов.
- Конкурентные операции не нарушают инварианты.
- Повтор submit не создаёт вторую заявку.
- Повтор события/команды не дублирует эффект.
- Техническая ошибка не превращается в `REJECTED`.
- Приостановка не меняет публичный статус и имеет причину/этап.
- Resume проверяет права, версию процесса, hold и терминальность заявки.
- Два параллельных resume не запускают два этапа.
- Возобновление и аудит фиксируются согласованно через локальную транзакцию и Outbox.
- Запоздавшее событие не меняет терминальное состояние.
- Повторное рассмотрение после `REJECTED` не реализуется в MVP.
