# Credit Flow Microservices — модель безопасности

**Статус:** Draft v1 · **Версия:** 1.0  
**Предположение:** учебное окружение использует только синтетические данные.

## 1. Цели
Защитить аккаунты, компании и заявки; разделить пользовательские и административные права; минимизировать передачу данных; исключить секреты из репозитория/логов; обеспечить аудит ключевых действий.

## 2. Границы доверия
1. Браузер — недоверенный клиент; валидация на сервере.
2. API Gateway — публичная точка входа, но не единственное место авторизации.
3. Бизнес-сервисы проверяют право на конкретный ресурс.
4. Kafka — внутренний транспорт, но сообщения всё равно валидируются.
5. PostgreSQL: отдельная роль и база на сервис.
6. CI/CD и registry — критичная граница поставки.
7. Локальная среда использует синтетические данные.

## 3. Аутентификация
- Регистрация по email и паролю, нормализация и уникальность email.
- Argon2id для password hashing с параметрами, зафиксированными и проверенными на целевом окружении.
- Короткоживущий access JWT.
- Refresh token с ротацией, хранением безопасного hash/идентификатора сессии и отзывом.
- Logout отзывает refresh-сессию.
- Rate limiting для входа/регистрации и ответы, не облегчающие перечисление аккаунтов.
- Не реализовывать криптографические примитивы самостоятельно; до реального применения рассмотреть OIDC provider и отдельный security review.

JWT validation: подпись и разрешённый сервером алгоритм, `iss`, `aud`, `exp`, `nbf` при применимости, subject/session ID и обязательные claims. Нельзя принимать алгоритм, ключ или issuer произвольно от клиента. Предусмотреть ротацию ключей.

## 4. Авторизация
Роли:
- `borrower`;
- `company_admin` — только в контексте конкретной компании;
- `platform_admin`;
- отдельная service identity для внутренних вызовов.

Проверять членство и права на каждый объект. UUID не является доказательством доступа. Административные маршруты требуют отдельной проверки. Сервисные запросы проверяют идентичность вызывающего сервиса и его полномочия.

## 5. Внутреннее взаимодействие
- REST/gRPC вызовы имеют timeout и trace context.
- Внутренние endpoints не публикуются наружу без необходимости.
- Production-модель предусматривает TLS и service-to-service authentication.
- Не доверять пользовательским `X-User-ID`/`X-Role`; Gateway удаляет/перезаписывает такие заголовки, downstream использует проверенный контекст/подтверждённую service identity.

Kafka:
- ACL по принципу наименьших привилегий.
- Producer пишет только в разрешённые топики; consumer читает только нужные топики/groups.
- TLS и ротация credentials в production.
- DLQ ограничивается по доступу и retention.

## 6. Защита данных
- Только синтетические данные в учебном окружении.
- Не логировать пароли, токены, cookies, полные документы или избыточные тела запросов.
- Не помещать чувствительные значения в metric labels и trace attributes.
- Передавать между сервисами минимум необходимых данных.
- В расширенной версии для документов: object storage, короткоживущие разрешённые ссылки, проверка MIME/размера, антивирусная обработка и политика удаления.
- До реальных данных определить сроки хранения и удаления.

## 7. Секреты и конфигурация
- `.env` в `.gitignore`; в репозитории только `.env.example` без реальных секретов.
- CI secrets передаются через защищённые настройки.
- Не печатать секреты при старте или ошибке конфигурации.
- Credentials БД разделены по сервисам.
- Kubernetes secrets не коммитятся открытым текстом; для production — secret manager или защищённый процесс доставки.
- Документировать ротацию ключей и credentials.

## 8. HTTP безопасность
- Серверная валидация данных.
- Лимиты размера тела и таймауты чтения.
- Rate limiting чувствительных операций.
- Безопасные response headers и CORS только для известных origin.
- CSRF-защита необходима, если браузер автоматически отправляет auth cookies; bearer token не отменяет XSS-риски.
- Ошибки не раскрывают stack trace, SQL и внутренние адреса.
- Не обращаться к произвольным пользовательским URL без отдельной SSRF-защиты.

## 9. Аудит
Фиксировать входы/выходы в нужном объёме, изменение ролей/членства, публикацию продуктов, изменение правил, административные действия и важные переходы статуса. Запись содержит actor, action, resource ID, timestamp, correlation ID и безопасные метаданные. Секреты и полные документы не сохраняются. Обычный пользователь не может менять аудит.

## 10. Контейнеры и поставка
- Контейнеры запускаются не от root, где возможно.
- Финальный image минимален; версии фиксируются, для релизов используются digest.
- CI проверяет тесты/линтеры; позднее добавляются dependency, secret и image scanning.
- Workflow имеет минимальные права; недоверенный код не получает release secrets.
- Kubernetes: requests/limits, probes, ограниченные service accounts.
- Секреты и административные endpoints не публикуются через ingress без необходимости.

## 11. Безопасность событий
- Проверка event type/version/required fields и размера сообщения.
- Deduplication по event ID.
- Сообщения из Kafka не считаются автоматически доверенными.
- Ошибочные сообщения карантинируются; бесконечные retry loops запрещены.
- Идемпотентность не заменяет авторизацию исходного API.

## 12. Минимальный security test plan
- Доступ к чужой компании/заявке.
- Вызов admin endpoint без роли.
- Просроченный/поддельный JWT.
- Повторное использование refresh token после ротации.
- Повтор idempotency key с изменённым телом.
- SQL injection в текстовых полях/фильтрах.
- Большое тело и неверный Content-Type.
- Подмена identity headers.
- Некорректное/слишком большое Kafka-сообщение.
- Отсутствие секретов/персональных данных в логах.
- Попытка доступа к БД с credentials другого сервиса.

## 13. Критерии приёмки
- Защищённые маршруты соответствуют матрице доступа.
- Проверяется владение/членство, а не только UUID.
- Секреты отсутствуют в Git и логах.
- Учётные данные сервисов разделены.
- Критические негативные сценарии автоматизированы.
- Документированы ограничения учебной реализации и требования до использования реальных данных.
